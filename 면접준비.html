01

1. 자기소개

안녕하세요. 숭실대학교 전자공학 전공 우상욱입니다.

저는 호기심이 많고 새로운 내용을 배우는 것을 좋아하는 편입니다. 그래서 전공 과목도 한쪽에만 치우치기보다 디지털 회로, 임베디드, 컴퓨터 구조, 시스템 쪽 과목을 폭넓게 들으려고 했고, 타과 과목인 시스템프로그래밍이나 운영체제도 수강하면서 하드웨어와 소프트웨어가 어떻게 맞물리는지 공부해 왔습니다.

이런 과정에서 Verilog-HDL로 회로 구조를 직접 만들고 FPGA에서 동작을 확인하는 RTL 설계에 특히 흥미를 느끼게 되었습니다. SoC나 디지털 회로설계는 하나의 지식만으로 해결하기보다 architecture, bus, firmware, 검증, timing이 함께 맞아야 하는 복잡한 분야라고 생각합니다. 제가 여러 분야를 배우려고 했던 성향과 기반이 이런 복잡한 문제를 이해하고, 협업 과정에서 다른 파트와 소통하는 데 도움이 될 것이라고 생각합니다.

앞으로는 이 기반 위에서 RTL 설계와 FPGA 검증을 더 깊게 공부하고 싶습니다. ETRI 디지털 RTL 회로설계 과정을 통해 제가 해왔던 폭넓은 학습을 실무형 설계 역량으로 연결하고 싶습니다.

안녕하세요. 전자공학 전공 우상욱입니다. 저는 호기심이 많고 배우는 것을 좋아해서 디지털 회로뿐 아니라 임베디드, 컴퓨터 구조, 시스템프로그래밍, 운영체제까지 폭넓게 공부하려고 했습니다. 그러다 Verilog-HDL로 회로 구조를 만들고 FPGA에서 동작을 확인하는 과정에 흥미를 느끼게 되었습니다. SoC 설계는 hardware, software, bus, 검증이 함께 맞아야 하는 복잡한 분야라고 생각하기 때문에, 제가 폭넓게 공부해 온 기반이 협업과 문제 해결에 도움이 될 것 같습니다. ETRI 과정에서 이 기반을 RTL 설계와 FPGA 검증 역량으로 더 깊게 발전시키고 싶습니다.

직무 관련 경험으로는 Verilog-HDL 기반 RTL 설계와 FPGA 구현 경험이 있습니다. 대표적으로 AXI-to-APB Bridge와 FPGA Video Filtering 프로젝트를 하면서 bus interface, timing, buffer 구조를 직접 고민했고, 이 경험을 통해 RTL 설계와 검증 쪽으로 진로를 구체화하게 되었습니다.

가장 자신 있는 프로젝트는 FPGA Video Filtering 가속기 설계입니다. 카메라 입력 영상을 FPGA에서 실시간 처리해 LCD로 출력하는 프로젝트였고, 저는 3x3 window 생성부와 LCD 출력 제어, top module 통합 검증을 주로 맡았습니다. 실제 보드에서 화면이 밀리거나 깨지는 문제가 있었는데, LCD timing과 frame buffer 흐름을 확인하면서 double buffering과 frame drop 기반 sync 구조로 안정화했습니다.

궁금한 것은 직접 공부하고 만들어보면서 이해하려고 하는 지원자라고 생각합니다. 또 SoC처럼 여러 분야가 연결되는 일을 할 때, 폭넓게 배운 기반을 바탕으로 다른 파트와 소통하며 문제를 풀어가고 싶습니다.

02

2. 공통질문

전공 프로젝트를 하면서 RTL 설계와 FPGA 구현이 제 적성에 잘 맞는다고 느꼈습니다. Verilog로 회로 구조를 만들고, testbench나 실제 FPGA 보드에서 동작을 확인하는 과정이 재미있었습니다. 그런데 프로젝트를 할수록 단순히 기능을 구현하는 것만으로는 부족하고, timing, interface, 검증 흐름까지 체계적으로 알아야 한다는 것도 느꼈습니다. ETRI 과정은 C 기반 알고리즘, Verilog-HDL 설계, FPGA 구현까지 이어지는 흐름을 배울 수 있어서 제가 부족하다고 느낀 부분을 가장 잘 채울 수 있는 과정이라고 생각해 지원했습니다.

제가 가장 흥미를 느낀 부분이 기능 요구사항을 RTL 구조로 옮기고, 실제 동작을 확인하는 과정이었기 때문입니다. Front-End 전체 흐름에도 관심은 있지만, 지금 제 단계에서는 Verilog-HDL로 구조를 정확히 설계하고, timing과 interface, 검증 관점을 먼저 탄탄히 잡는 것이 우선이라고 생각했습니다.

실무형 RTL 설계 흐름과 FPGA 검증 과정을 가장 배우고 싶습니다. 프로젝트에서 testbench와 waveform debug는 해봤지만, 산업 현장에서 요구하는 설계 품질 관리나 timing constraint 분석은 아직 부족하다고 느낍니다. 이 부분을 교육 과정에서 집중적으로 보완하고 싶습니다.

저는 RTL과 FPGA 프로젝트를 직접 해본 경험이 있어서 교육 내용을 실제 설계 상황과 연결해 빠르게 이해할 수 있다고 생각합니다. 특히 AXI-to-APB Bridge나 FPGA Video Filtering 프로젝트를 하며 interface, timing, buffer 문제를 직접 겪어봤습니다. 동시에 실무 수준의 검증과 설계 flow는 더 배워야 한다는 것도 알고 있기 때문에, 교육에 성실히 참여해 부족한 부분을 빠르게 채우고 싶습니다.

직접 부딪혀 본 경험이 있다는 점이 강점이라고 생각합니다. 단순히 RTL 문법만 공부한 것이 아니라, AXI-to-APB Bridge에서는 protocol 변환을 고민했고, FPGA Video Filtering에서는 실제 보드에서 timing과 frame buffer 문제를 겪었습니다. 이런 경험 덕분에 교육 내용을 단순 이론이 아니라 실제 설계 상황과 연결해서 받아들일 수 있을 것 같습니다.

디지털 회로설계 엔지니어로 성장하고 싶습니다. 단순히 Verilog 코드를 작성하는 엔지니어가 아니라, architecture 의도를 이해하고 datapath, control path, interface, verification까지 함께 고려할 수 있는 엔지니어가 목표입니다.

기능 요구사항을 clock 기반 hardware 구조로 정확히 바꾸는 능력이라고 생각합니다. 여기에 timing, reset, interface protocol, verification을 함께 고려해야 좋은 RTL이 된다고 생각합니다. 구현만 되는 코드보다 검증 가능하고 확장 가능한 구조를 만드는 역량이 중요하다고 봅니다.

그렇게 보일 수 있다고 생각합니다. 다만 저는 프로젝트를 단순히 많이 나열하기보다 각 프로젝트에서 다른 설계 요소를 배우려고 했습니다. FIR에서는 datapath, AES에서는 register interface, AXI-to-APB에서는 bus protocol, FPGA Video Filtering에서는 실제 board timing과 buffer 구조, UVM에서는 검증 환경을 경험했습니다. 아직 실무 수준으로 깊다고 말하기는 어렵지만, SoC 설계 요소들이 어떻게 연결되는지 이해하는 기반을 만들었다고 생각합니다.

학부 프로젝트는 기능 구현에 초점이 맞춰지는 경우가 많지만, 실무에서는 검증 가능성, timing, 재사용성, 문서화, 협업 flow까지 함께 중요하다고 생각합니다. 프로젝트를 하면서 기능이 동작해도 실제 보드에서 timing이나 interface 문제가 생길 수 있다는 것을 느꼈고, 그래서 실무형 설계 flow를 더 배우고 싶습니다.

저는 아직 배워야 할 부분이 많지만, RTL 설계와 FPGA 구현을 직접 해보면서 이 분야로 진로를 구체화해 왔습니다. 프로젝트를 통해 단순 구현보다 timing, interface, 검증 흐름을 함께 보는 것이 중요하다는 점을 느꼈고, 그래서 더 체계적으로 배우고 싶다는 목표가 생겼습니다. ETRI 과정에서 성실히 배우고, 교육 이후 디지털 회로설계 직무에서 빠르게 성장할 수 있는 기본기를 갖추고 싶습니다.

03

3. 전공질문 - 공통

이 파트는 면접관이 한 명씩 돌아가며 묻거나, 같은 질문에 지원자들이 순서대로 답할 가능성이 높습니다. 답변은 너무 길게 하지 말고 정의 -> 중요성 -> 프로젝트 연결 순서로 말합니다.

RTL은 Register Transfer Level의 약자로, clock edge 사이에서 register 간 data가 어떻게 이동하고 어떤 combinational logic을 거치는지 표현하는 설계 수준입니다. Verilog-HDL로 작성한 RTL은 synthesis를 통해 gate-level 회로로 변환될 수 있습니다.

조합논리는 현재 입력만으로 출력이 결정되는 회로이고, 순차논리는 clock과 register에 의해 이전 상태가 현재 출력에 영향을 주는 회로입니다. 조합논리는 always @(*), 순차논리는 always @(posedge clk) 형태로 주로 작성합니다.

Blocking assignment =는 순차적으로 즉시 값이 반영되고, non-blocking assignment <=는 RHS를 먼저 평가한 뒤 같은 time step 끝에서 동시에 update됩니다. 일반적으로 조합논리는 blocking, clocked sequential logic은 non-blocking을 사용합니다.

조합논리에서 모든 조건에 대해 출력이 할당되지 않으면 이전 값을 유지해야 하므로 latch가 추론될 수 있습니다. 방지하려면 default 값을 먼저 주거나, if/else, case의 모든 branch에서 값을 명확히 할당해야 합니다.

상태 정의, 전이 조건, 출력 생성을 명확히 나누는 것이 중요합니다. reset 상태, illegal state 처리, handshake timing을 고려해야 하며, 보통 state register와 next-state logic을 분리해 설계합니다.

Setup time은 clock edge 전에 data가 안정적으로 유지되어야 하는 시간이고, hold time은 clock edge 후에도 data가 유지되어야 하는 시간입니다. Setup violation은 경로 delay가 너무 길 때, hold violation은 data path가 너무 짧거나 clock skew 영향이 클 때 발생할 수 있습니다.

Flip-flop 입력이 setup/hold time을 만족하지 못하면 출력이 0이나 1로 바로 안정되지 못하고 중간 상태에 머무를 수 있는데, 이를 metastability라고 합니다. CDC 상황에서 자주 문제가 되며 synchronizer로 확률을 줄입니다.

CDC는 clock domain crossing 문제입니다. 서로 다른 clock domain 사이에서 signal을 전달할 때 metastability나 data incoherency가 생길 수 있습니다. 단일 bit control signal은 2-stage synchronizer, multi-bit data는 handshake나 async FIFO를 사용합니다.

FIFO는 producer와 consumer의 속도 차이를 흡수하거나 clock domain이 다른 두 블록 사이에서 data를 안정적으로 전달하기 위해 사용합니다. full/empty flag, read/write pointer, overflow/underflow 방지가 중요합니다.

AXI는 고성능 bus로 read/write channel이 분리되어 있고 burst transfer를 지원합니다. APB는 setup phase와 enable phase로 동작하는 단순한 peripheral bus입니다. AXI는 throughput이 중요할 때, APB는 register 기반 peripheral 제어에 적합합니다.

source가 valid를 올려 data가 유효함을 알리고, destination이 ready를 올려 받을 준비가 되었음을 알립니다. valid와 ready가 같은 cycle에 모두 1일 때 transfer가 발생합니다. valid는 ready를 기다렸다가 올리는 것이 아니라 data가 준비되면 유지해야 합니다.

Setup phase에서는 PSEL이 올라가고 address, write/read, write data가 준비됩니다. 다음 cycle enable phase에서 PENABLE이 올라가고, PREADY가 1이면 transfer가 완료됩니다. PREADY가 0이면 enable phase를 유지하며 wait-state가 들어갑니다.

SoC 내부에서 CPU나 DMA는 AXI를 사용하고, UART, GPIO, Timer 같은 저속 peripheral은 APB로 제어하는 경우가 많습니다. 따라서 AXI transaction을 APB transfer로 변환하는 bridge가 필요합니다. 제 프로젝트에서는 AXI burst를 APB single transfer로 분해하고 address decoding, PREADY wait-state, error response를 처리했습니다.

reset 이후 초기 상태, 정상 동작 scenario, corner case, expected result와 actual result 비교를 확인합니다. 가능하면 waveform만 보는 것이 아니라 reference model이나 scoreboard로 자동 비교하는 것이 좋다고 생각합니다.

simulation은 이상적인 조건에서 동작하는 경우가 많지만, 실제 보드에서는 timing constraint, CDC, external device timing, reset sequence, IO delay 문제가 생길 수 있습니다. FPGA Video Filtering 프로젝트에서도 testbench보다 실제 LCD timing과 frame sync가 더 중요했습니다.

합성 가능한 문법을 사용하고, 조합논리와 순차논리를 명확히 구분해야 합니다. latch가 생기지 않도록 모든 branch에서 값을 할당하고, delay나 file IO 같은 testbench용 문법을 DUT에 넣지 않아야 합니다.

driver는 sequence item을 DUT interface signal로 변환해 구동하는 역할이고, monitor는 DUT interface를 관찰해 transaction으로 복원하는 역할입니다. 즉 driver는 입력을 넣고, monitor는 동작을 관찰합니다.

scoreboard는 expected result와 actual result를 비교해 DUT가 맞게 동작했는지 판단하는 역할입니다. 사람이 waveform을 눈으로 보는 것보다 반복 검증과 corner case 확인에 유리합니다.

04

4. 전공질문 - 선착순 맞히기

이 파트는 짧고 정확하게 답하는 것이 핵심입니다. 아래는 “정답 한 줄 + 보충 한 줄” 형식으로 외우면 좋습니다.

non-blocking assignment(<=)입니다. clock edge에서 register들이 동시에 update되는 동작을 표현하기 위해 사용합니다.

모든 조건에서 출력이 할당되도록 default assignment를 주거나 모든 branch를 채워야 합니다.

회로의 초기 상태를 명확히 정하기 위해 필요합니다. 특히 FSM이나 counter는 reset 상태가 없으면 예측하기 어려운 상태에서 시작할 수 있습니다.

bit width나 depth 같은 값을 재사용 가능하게 만들기 위해 사용합니다. 설계 변경 시 코드 수정 범위를 줄일 수 있습니다.

bit 해석 방식이 달라 결과가 달라질 수 있습니다. 곱셈, 비교, 확장 연산에서 특히 주의해야 합니다.

simulation은 RTL 동작을 검증하는 과정이고, synthesis는 RTL을 gate-level 회로로 변환하는 과정입니다.

같은 simulation time에 여러 assignment나 event 순서가 불명확할 때 생길 수 있습니다. 순차회로에서는 non-blocking 사용으로 줄일 수 있습니다.

combinational path를 줄이거나 pipeline register를 추가하고, timing constraint를 확인합니다.

data path delay를 늘리거나 clock skew를 조정하는 방식으로 해결합니다. FPGA에서는 tool이 buffer 삽입 등으로 해결하는 경우도 있습니다.

2-stage synchronizer를 사용합니다. metastability가 다음 logic으로 전파될 확률을 줄이기 위한 구조입니다.

handshake나 async FIFO를 사용합니다. 여러 bit가 서로 다른 cycle에 잡히는 문제를 피하기 위해서입니다.

pointer crossing 시 한 번에 한 bit만 변하게 하여 clock domain crossing 오류 가능성을 줄이기 위해 사용합니다.

완전히 없애기는 어렵고 확률을 충분히 낮추는 방식으로 대응합니다. synchronizer를 사용하는 이유도 그 때문입니다.

valid와 ready가 같은 cycle에 모두 1일 때 transfer가 발생합니다.

그대로 보낼 수 없습니다. APB는 burst를 지원하지 않기 때문에 AXI burst를 여러 APB single transfer로 분해해야 합니다.

setup phase 다음 cycle인 enable phase에서 올라갑니다.

PREADY가 0인 동안 enable phase를 유지해 wait-state를 표현합니다.

APB slave를 선택하는 signal입니다. address decoding 결과에 따라 특정 slave의 PSEL이 활성화됩니다.

AXI-Lite는 단순 register access용으로 burst를 지원하지 않고, AXI4는 burst transfer를 지원하는 고성능 bus입니다.

CPU가 계속 polling하지 않고 peripheral event나 연산 완료를 알 수 있게 하기 위해 사용합니다.

Moore FSM은 출력이 현재 state에만 의존하고, Mealy FSM은 현재 state와 input에 함께 의존합니다.

긴 combinational path를 여러 stage로 나누어 clock frequency를 높이기 위해 사용합니다.

throughput은 단위 시간당 처리량이고, latency는 입력부터 출력까지 걸리는 시간입니다.

DSP block이나 LUT 자원을 많이 사용하고 timing path도 길어질 수 있기 때문입니다.

대칭 FIR coefficient에서 h[k] = h[N-1-k] 관계를 이용할 수 있기 때문입니다.

multi-byte data를 저장하거나 해석할 때 byte 순서가 달라 결과가 달라지는 문제입니다.

directed test는 특정 scenario를 의도적으로 검증하고, random test는 다양한 입력 조합을 통해 예상 못한 corner case를 찾는 데 유리합니다.

어떤 기능과 scenario가 검증되었는지 정량적으로 확인하기 위해 봅니다.

protocol rule이나 timing 관계가 깨졌을 때 즉시 검출하기 위해 사용합니다.

DUT 결과가 맞는지 비교할 기준이 필요하기 때문입니다. AES 프로젝트에서는 Python AES 결과를 golden data로 사용했습니다.

reset, clock, valid/ready 같은 control signal, FSM state, data path 순서로 확인합니다.

05

5. 공통질문 - 인성질문

문제가 생겼을 때 감정적으로 흔들리기보다 원인을 하나씩 확인하는 편입니다. FPGA Video Filtering 프로젝트에서 화면이 깨지는 문제가 있었을 때도 단순히 연산부 문제로만 보지 않고, 카메라 입력, frame buffer, LCD 출력 timing을 나눠서 확인했습니다. 이런 성향이 RTL debug나 waveform 분석에 잘 맞는다고 생각합니다.

처음에는 실패 가능성을 줄이려고 목표를 보수적으로 잡는 경향이 있었습니다. 하지만 프로젝트를 하면서 완벽히 준비된 상태에서 시작하는 경우는 많지 않고, 구현하고 검증하면서 배우는 것이 많다는 것을 느꼈습니다. 그래서 최근에는 큰 목표를 작은 단계로 나누어 실행하고, 파형과 결과를 보며 개선하는 방식으로 보완하고 있습니다.

STM32 Mini Elevator 프로젝트에서 팀원 중 일부는 MCU 경험이 많지 않았습니다. 혼자 구현하면 빠를 수도 있었지만, 팀 프로젝트의 목표는 함께 완성하는 것이라고 생각했습니다. 기능을 입력부, 표시부, 모터 제어, 상태 로직으로 나누고 각자 맡은 부분을 이해할 수 있도록 같이 스터디했습니다. 이후 제가 맡은 Step Motor와 전체 상태 로직에 팀원들의 모듈을 연결해 최종 시연 가능한 형태로 통합했습니다.

FPGA Video Filtering 프로젝트에서 처음에는 convolution 연산부 성능 개선에 집중했지만, 실제 보드에서는 화면 깨짐 문제가 계속 발생했습니다. 이후 문제를 연산부만 보지 않고 frame buffer, LCD timing, 입력/출력 sync 관점으로 다시 나누어 원인을 좁혔습니다. 이 경험을 통해 실제 hardware system에서는 개별 module 성능뿐 아니라 전체 data flow와 timing 정합이 중요하다는 것을 배웠습니다.

문제를 크게 보지 않고 작은 단위로 나누어 따라가겠습니다. RTL 설계도 module, interface, timing, testbench 단위로 나누면 해결 가능한 부분이 보인다고 생각합니다. 매일 배운 내용을 정리하고 실습 결과를 재현하면서 따라가고, 혼자 해결이 안 되는 부분은 질문과 스터디로 빠르게 보완하겠습니다.

실무 수준의 검증 방법론과 timing closure 경험은 아직 부족하다고 생각합니다. 프로젝트에서 testbench와 waveform debug, 기초 UVM은 해봤지만, 복잡한 SoC나 IP에서 coverage-driven verification을 깊게 수행한 경험은 제한적입니다. FPGA 구현 경험은 있지만 constraint 설정과 timing report 분석도 더 배워야 합니다.

저는 팀에서 전체 흐름을 정리하고 각 기능이 잘 연결되도록 맞추는 역할을 자주 맡았습니다. STM32 프로젝트에서는 팀장으로 Step Motor 제어와 전체 통합을 담당했고, FPGA Video Filtering 프로젝트에서도 Window3x3 연산부와 LCD 출력부를 top module에서 연결하며 시스템 동작을 확인했습니다.

문제가 생기면 먼저 원인을 쪼개서 확인합니다. 막연히 어렵다고 느끼면 스트레스가 커지지만, clock, reset, FSM, interface, data path처럼 확인할 단위를 나누면 할 일이 명확해집니다. 평소에는 기록하면서 진행해 같은 문제를 반복하지 않으려고 합니다.

오히려 배울 기회라고 생각합니다. 제가 아는 부분은 공유하고, 부족한 부분은 빠르게 질문하면서 따라가겠습니다. 특히 설계나 검증 방식에서 더 좋은 방법을 배우면 제 프로젝트 경험과 연결해 흡수하려고 할 것 같습니다.

상황에 따라 다르지만, 전체 구조를 정리하거나 통합이 필요한 상황에서는 리더 역할을 맡는 편입니다. 반대로 특정 분야를 더 잘 아는 팀원이 있으면 그 방향을 따르면서 제가 맡은 부분을 정확히 수행하려고 합니다. 중요한 것은 역할보다 팀 결과물이 제대로 동작하는 것이라고 생각합니다.

  1. 교육 과정 중 RTL 설계 실습과 FPGA 구현 실습의 비중이 어느 정도인지 궁금합니다.
  2. 수료 프로젝트가 있다면 개인 프로젝트 중심인지, 팀 프로젝트 중심인지 궁금합니다.
  3. 교육 과정에서 실제 기업 직무와 연결되는 설계·검증 tool flow를 어느 정도까지 경험할 수 있는지 궁금합니다.
06

6. 후기 기반 추가 대비 질문

실제 후기에서 반복된 질문을 기준으로 정리한 파트입니다. 7대7 면접에서는 답변이 길면 흐름이 늘어질 수 있으니, 아래 답변을 20~40초 안에 말하는 연습을 합니다.

힘든 상황이 생기면 먼저 무엇 때문에 힘든지 원인을 나누어 볼 것 같습니다. 업무량 문제인지, 기술적으로 막힌 것인지, 소통 문제인지 구분해야 해결 방법이 달라진다고 생각합니다. 기술적으로 막힌 부분은 혼자 오래 붙잡기보다 제가 확인한 내용과 시도한 방법을 정리해서 질문하고, 업무량이 문제라면 우선순위와 일정을 조율하겠습니다. 프로젝트를 할 때도 문제가 생기면 파형, timing, interface처럼 단위를 나누어 확인하는 방식으로 해결해 왔습니다.

저는 스트레스를 막연하게 두면 더 커지는 편이라, 먼저 할 일을 작은 단위로 쪼개서 정리합니다. 예를 들어 설계 문제가 생기면 clock, reset, FSM, interface, data path처럼 확인할 순서를 적어두고 하나씩 지워갑니다. 이렇게 하면 감정적으로 부담을 느끼기보다 실제로 해결할 수 있는 문제로 바뀌어서 스트레스가 줄어듭니다.

처음에는 아쉬울 수 있지만, 배정된 팀에서 배울 수 있는 부분을 먼저 찾겠습니다. 제가 원하는 RTL 설계와 직접적으로 같지 않더라도, 반도체 설계 업무는 검증, tool flow, 문서화, 협업 방식이 서로 연결되어 있다고 생각합니다. 맡은 자리에서 필요한 역량을 성실히 쌓고, 이후 기회가 생겼을 때 제가 원하는 방향으로 확장하겠습니다.

우선 맡은 업무의 목적과 제가 배울 수 있는 부분을 이해하려고 하겠습니다. 희망 직무가 RTL 설계라고 해도 검증, FPGA, firmware, tool flow 경험은 설계 역량과 연결된다고 생각합니다. 다만 장기적으로는 디지털 회로설계 쪽으로 성장하고 싶기 때문에, 맡은 업무를 잘 수행하면서도 관련 역량을 꾸준히 쌓고 기회가 있을 때 방향성을 말씀드리겠습니다.

초기에는 연봉 자체보다 제가 성장할 수 있는 직무와 환경이 더 중요하다고 생각합니다. 물론 현실적인 조건도 중요하지만, 제가 원하는 디지털 회로설계 분야에서 실무 경험을 쌓고 역량을 키울 수 있다면 장기적으로 더 큰 가치가 있다고 봅니다. 먼저 주어진 환경에서 실력을 증명하고, 이후 역량에 맞는 평가를 받을 수 있도록 하겠습니다.

바로 반박하기보다는 먼저 지시의 배경과 목적을 확인하겠습니다. 제가 이해하지 못한 제약이나 일정, 품질 기준이 있을 수 있기 때문입니다. 그래도 기술적으로 문제가 있다고 판단되면, 단순히 “안 됩니다”라고 말하기보다 예상되는 문제와 대안을 정리해서 말씀드리겠습니다.

제 의견을 고집하기보다 근거를 기준으로 이야기하겠습니다. 예를 들어 설계 방식에 의견 차이가 있다면 timing, resource, 검증 가능성, 일정 측면에서 장단점을 정리해 비교하겠습니다. 최종 결정이 제 의견과 다르더라도 결정된 방향을 따르되, 리스크가 있다면 미리 공유하겠습니다.

먼저 갈등의 원인이 기술적 의견 차이인지, 역할 분담 문제인지, 소통 문제인지 구분하겠습니다. 기술적 문제라면 data나 실험 결과를 기준으로 이야기하고, 역할 문제라면 해야 할 일을 다시 나누겠습니다. STM32 팀 프로젝트에서도 팀원들의 경험 차이가 있었지만, 기능을 나누고 같이 스터디하면서 최종 통합까지 진행한 경험이 있습니다.

저는 Verilog-HDL 기반 RTL 설계와 FPGA 구현 중심으로 프로젝트를 진행했습니다. 대표적으로 FIR Filter, AES-128 IP, AXI-to-APB Bridge를 설계했고, FPGA Video Filtering 프로젝트에서는 카메라 입력 영상을 FPGA에서 실시간 처리해 LCD로 출력하는 시스템을 구현했습니다. 최근에는 RISC-V core 기반 Mini MCU와 UVM 기초 검증 환경도 구성해 보았습니다.

FPGA Video Filtering 프로젝트가 가장 좋다고 생각합니다. RTL 설계, FPGA 구현, C 기반 PS 제어, 실제 보드 검증이 함께 들어가 있어서 ETRI 과정과 연결하기 좋습니다. 특히 실제 보드에서 화면 깨짐 문제가 발생했을 때, 연산부만 보는 것이 아니라 LCD timing과 frame buffer 흐름을 나누어 확인하며 해결한 경험을 말할 수 있습니다.

OV5640 카메라 입력 영상을 Ultra96-V2 FPGA에서 실시간 처리해 LCD로 출력하는 프로젝트입니다. PS는 C 코드로 카메라 초기화와 필터 모드 제어를 맡고, PL은 Verilog-HDL로 line buffer, 3x3 window 생성, convolution, LCD 출력 제어를 수행했습니다. 저는 3x3 window 생성부와 LCD 출력 제어, top module 통합 검증을 주로 담당했습니다.

실제 보드에서 화면이 밀리거나 frame이 깨지는 문제가 있었습니다. 처음에는 convolution 연산부 문제로 생각했지만, 확인해 보니 카메라 입력과 LCD 출력 timing, frame buffer 전환 시점이 더 중요했습니다. 그래서 LCD timing parameter를 조정하고, double buffering과 frame drop 기반 sync 구조로 안정화했습니다.

FPGA Video Filtering에서는 3x3 window 생성을 위한 line buffer/shift register 구조와 LCD output buffer 제어를 맡았습니다. 또한 PS 측 C 코드 일부와 top module 통합 검증도 함께 진행했습니다. 단순히 개별 모듈만 만든 것이 아니라, 실제 보드에서 입력-처리-출력 흐름이 맞는지 확인했습니다.

실제 hardware system에서는 개별 연산부가 맞게 동작하는 것만으로 충분하지 않다는 점을 배웠습니다. 카메라, 연산 pipeline, LCD 출력처럼 서로 다른 timing을 가진 블록이 연결되면 buffer 구조와 sync가 매우 중요합니다. 이 경험 때문에 RTL 설계에서도 interface와 검증 관점을 함께 봐야 한다고 느꼈습니다.

Fixed point는 소수점 위치를 미리 고정해 정수를 스케일링해서 실수를 표현하는 방식입니다. 예를 들어 Q-format처럼 전체 bit 중 일부는 정수부, 일부는 소수부로 정해 둡니다. Floating point는 부호, 지수, 가수로 수를 표현해서 훨씬 넓은 범위의 값을 표현할 수 있습니다. 대신 hardware 구현은 floating point가 더 복잡합니다.

일반적으로 fixed point가 더 유리합니다. fixed point는 정수 연산기 기반으로 구현할 수 있어 multiplier, adder, register 구조가 단순하고 면적과 전력 소모가 작습니다. 반면 floating point는 exponent alignment, normalization, rounding 같은 과정이 필요해서 hardware가 복잡하고 resource를 더 많이 사용합니다.

AI 연산은 MAC 연산이 매우 많이 반복되기 때문에 연산기 면적과 전력 효율이 중요합니다. Floating point는 표현 범위가 넓지만 hardware cost가 크기 때문에, inference에서는 정확도를 크게 잃지 않는 범위에서 INT8, INT16, fixed point 같은 표현을 많이 사용합니다. 이렇게 하면 같은 면적과 전력에서 더 많은 연산을 처리할 수 있습니다.

표현 가능한 수의 범위가 넓고, 매우 큰 값과 작은 값을 동시에 다루기 좋습니다. scaling을 사람이 세밀하게 정하지 않아도 되기 때문에 algorithm 개발이나 training 단계에서는 floating point가 편리합니다. 다만 hardware 구현 관점에서는 비용이 커서, inference accelerator에서는 fixed point나 integer quantization을 많이 사용합니다.

표현 범위와 정밀도가 제한됩니다. 소수점 위치를 잘못 정하면 overflow가 나거나 작은 값이 quantization error로 사라질 수 있습니다. 그래서 fixed point를 사용할 때는 data range 분석, scaling factor, bit width, saturation 처리 등을 함께 고려해야 합니다.

Q-format은 fixed point에서 정수부와 소수부 bit 수를 정해 표현하는 방식입니다. 예를 들어 Q1.15는 1bit 정수부와 15bit 소수부를 사용해 값을 표현합니다. hardware에서는 실제로 정수처럼 저장하지만, 해석할 때 정해진 scaling을 적용해 소수로 봅니다.

Quantization은 floating point 값을 더 낮은 bit width의 fixed point나 integer 값으로 근사하는 과정입니다. AI inference에서는 FP32 모델을 INT8 등으로 변환해 연산량, memory bandwidth, 전력 소모를 줄일 수 있습니다. 대신 정확도 손실이 생길 수 있어 calibration이나 quantization-aware training을 사용하기도 합니다.

Overflow가 발생했을 때 saturation은 최대값이나 최소값에 고정하는 방식이고, wrap-around는 bit가 넘치면서 값이 순환하는 방식입니다. 신호처리나 AI 연산에서는 wrap-around가 큰 오차를 만들 수 있어 saturation을 쓰는 경우가 많습니다.

Setup time은 clock edge가 오기 전에 data가 안정적으로 유지되어야 하는 최소 시간이고, hold time은 clock edge 이후에도 data가 안정적으로 유지되어야 하는 최소 시간입니다. 이 조건을 만족해야 flip-flop이 의도한 값을 안정적으로 저장할 수 있습니다.

Flip-flop이 잘못된 값을 저장하거나 metastability가 발생할 수 있습니다. 그 결과 회로가 simulation과 다르게 동작하거나, 특정 clock frequency에서만 오류가 발생할 수 있습니다. setup violation은 주로 data path delay가 너무 길 때, hold violation은 data path가 너무 짧거나 clock skew 영향이 클 때 발생합니다.

combinational logic delay를 줄이거나 pipeline register를 추가해 critical path를 나눌 수 있습니다. 또는 clock frequency를 낮추거나 synthesis/PnR optimization, timing constraint를 확인하는 방식으로 해결합니다.

data path가 너무 빨리 도착하지 않도록 delay buffer를 추가하거나 clock skew를 조정해 해결합니다. FPGA나 ASIC tool이 hold fixing을 위해 buffer를 삽입하는 경우도 있습니다. setup과 달리 clock period를 늘린다고 항상 해결되는 문제는 아니라는 점이 중요합니다.

setup violation이 clock 주파수와 더 직접적으로 관련 있습니다. clock period가 짧아지면 data가 다음 clock edge 전에 도착할 시간이 부족해지기 때문입니다. hold violation은 같은 clock edge 직후의 안정성 문제라 clock period를 늘리는 것만으로 해결되지 않는 경우가 많습니다.

설계가 목표 clock frequency에서 setup/hold timing constraint를 모두 만족하도록 만드는 과정입니다. RTL 구조, constraint, synthesis, placement/routing 결과를 함께 보며 critical path를 줄이고 timing violation을 해결합니다.

Laplace Transform을 사용합니다. 시간 영역의 연속시간 signal을 complex frequency domain인 s-domain으로 변환해 system의 pole, zero, stability, transient response 등을 분석할 수 있습니다.

Fourier Transform을 사용합니다. 연속시간 signal은 Fourier Transform, 이산시간 또는 sampled data는 DFT를 사용하고, 실제 계산에서는 빠른 알고리즘인 FFT를 많이 사용합니다.

Fourier Transform은 time domain signal을 여러 frequency 성분의 합으로 분해하는 변환입니다. 어떤 signal에 어떤 주파수 성분이 얼마나 포함되어 있는지 볼 수 있기 때문에, 필터 설계나 신호 분석에서 중요합니다.

Fourier Transform은 주로 steady-state frequency 성분을 분석하는 데 사용하고, Laplace Transform은 s-domain에서 transient response와 stability까지 분석하기 좋습니다. 간단히 말하면 Fourier Transform은 jω 축에서의 frequency 분석이고, Laplace Transform은 s = σ + jω를 사용하는 더 일반적인 변환으로 볼 수 있습니다.

DFT는 discrete signal의 frequency 성분을 계산하는 변환이고, FFT는 DFT를 빠르게 계산하는 알고리즘입니다. 결과의 의미는 같지만 FFT는 계산량을 크게 줄여 실제 signal processing에서 많이 사용합니다.

연속 신호를 손실 없이 복원하려면 sampling frequency가 signal의 최대 frequency의 2배 이상이어야 한다는 정리입니다. 이를 Nyquist rate라고도 합니다. 만족하지 못하면 aliasing이 발생할 수 있습니다.

sampling frequency가 충분히 높지 않을 때 높은 frequency 성분이 낮은 frequency 성분처럼 잘못 나타나는 현상입니다. 이를 줄이기 위해 sampling 전에 anti-aliasing filter를 사용합니다.

신호처리에서 convolution은 입력 signal이 system의 impulse response를 통과했을 때 출력이 어떻게 되는지를 나타냅니다. 즉 LTI system의 출력은 입력과 impulse response의 convolution으로 표현할 수 있습니다. FIR Filter도 입력 sample과 coefficient를 convolution하는 구조로 볼 수 있습니다.

time domain에서 convolution은 frequency domain에서 multiplication으로 바뀝니다. 이를 convolution theorem이라고 합니다. 그래서 filter의 time-domain convolution은 frequency domain에서는 입력 spectrum에 filter frequency response를 곱하는 것으로 해석할 수 있습니다.

CNN에서 convolution은 image나 feature map 위를 kernel이 이동하면서 지역적인 특징을 추출하는 연산입니다. edge, texture, pattern 같은 local feature를 찾는 데 사용됩니다. hardware 관점에서는 multiply-accumulate 연산이 반복되는 구조라 line buffer, window generator, MAC array 같은 구조로 구현할 수 있습니다.

개념적으로는 kernel을 이용해 주변 값의 weighted sum을 계산한다는 점에서 비슷합니다. 다만 딥러닝 framework에서 말하는 convolution은 수학적으로 kernel을 뒤집지 않는 cross-correlation 형태로 구현되는 경우가 많습니다. 면접에서는 “지역 특징을 추출하는 weighted sum 연산”이라고 설명하면 충분합니다.

MAC 연산량이 많기 때문에 data reuse와 memory access를 줄이는 것이 중요합니다. 영상 처리에서는 line buffer와 window generator로 3x3 window를 만들고, CNN accelerator에서는 input feature map, weight, partial sum을 효율적으로 재사용하는 구조가 중요합니다.

FPGA Video Filtering 프로젝트에서 3x3 convolution 기반 영상 필터링을 구현했습니다. line buffer와 shift register로 매 clock 3x3 window를 만들고, 각 pixel에 filter coefficient를 곱해 더하는 방식으로 처리했습니다. 이 경험을 통해 convolution이 algorithm으로는 단순해 보여도 hardware에서는 buffer 구조와 timing이 중요하다는 것을 배웠습니다.

FIR Filter의 출력은 입력 sample들과 filter coefficient의 weighted sum으로 계산되며, 이는 time-domain convolution입니다. 제가 진행한 79-tap FIR Filter 프로젝트도 delay chain에 저장된 sample과 coefficient를 곱해 누적하는 구조였습니다.

CNN 계열 모델에서 convolution은 feature extraction의 핵심 연산이고, 연산량 대부분을 차지하는 경우가 많습니다. 따라서 AI accelerator에서는 convolution의 MAC 연산을 병렬화하고 data reuse를 높이는 구조가 성능과 전력 효율에 큰 영향을 줍니다.

7. 순서별 암기 시트

안녕하세요. 전자공학 전공 우상욱입니다. 저는 호기심이 많고 배우는 것을 좋아해서 디지털 회로뿐 아니라 임베디드, 컴퓨터 구조, 시스템프로그래밍, 운영체제까지 폭넓게 공부하려고 했습니다. 그 과정에서 Verilog-HDL로 회로 구조를 만들고 FPGA에서 동작을 확인하는 RTL 설계에 흥미를 느꼈습니다. SoC 설계는 architecture, bus, firmware, 검증, timing이 함께 맞아야 하는 복잡한 분야라고 생각하기 때문에, 제가 폭넓게 공부해 온 기반이 협업과 문제 해결에 도움이 될 것 같습니다. ETRI 과정에서 이 기반을 RTL 설계와 FPGA 검증 역량으로 더 깊게 발전시키고 싶습니다.
프로젝트를 통해 RTL 설계와 FPGA 구현이 제 적성에 맞는다고 느꼈습니다. 동시에 timing, interface, 검증 방법론처럼 혼자 공부만으로는 부족한 부분도 느꼈습니다. 그래서 ETRI 과정에서 RTL 구현부터 FPGA 검증까지 이어지는 흐름을 체계적으로 배우고 싶어 지원했습니다.
RTL은 register 간 data 이동과 combinational logic을 clock 기준으로 표현하는 설계 수준입니다. 좋은 RTL은 기능뿐 아니라 timing, reset, interface, verification을 함께 고려해야 합니다.
빠르게 말하되, 모르면 넘긴다. 아는 문제에서 정확히 한 문장으로 답한다.
저는 문제가 생겼을 때 바로 단정하기보다, 원인을 작은 단위로 나눠서 확인하는 편입니다. FPGA 프로젝트에서도 화면 깨짐 문제를 연산부만 보지 않고 timing, buffer, sync 구조로 나누어 확인하며 해결한 경험이 있습니다.
